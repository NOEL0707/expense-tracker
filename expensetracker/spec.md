# Technical Requirement Document (TRD) - Expense Tracker

## 1. Entity-Relationship (ER) Model

The application requires a simple data model to store expense records. To handle money accurately, we will store the `amount` either as an integer (representing the smallest currency unit, e.g., paise/cents) or a precise decimal, depending on the chosen database. For idempotency (handling network retries), we include an `idempotency_key`.

**Table: `expenses`**

| Column Name       | Data Type      | Constraints                          | Description                                             |
| ----------------- | -------------- | ------------------------------------ | ------------------------------------------------------- |
| `id`              | UUID / Integer | Primary Key                          | Unique identifier for the expense                       |
| `amount`          | Integer        | Not Null, > 0                        | Amount in the smallest currency unit (e.g., cents/paise) to avoid floating-point errors |
| `category`        | String/Varchar | Not Null                             | The category of the expense (e.g., Food, Transport)     |
| `description`     | String/Text    | Optional                             | A brief description of the expense                      |
| `date`            | Date           | Not Null                             | The date the expense occurred                           |
| `idempotency_key` | String         | Unique, Optional                     | Used to prevent duplicate entries on client retries     |
| `created_at`      | Timestamp      | Default Current Time                 | Record creation timestamp                               |

## 2. API Specification

The REST API will be responsible for creating and retrieving expenses.

### 2.1. Create Expense
- **Endpoint:** `POST /api/expenses`
- **Description:** Creates a new expense entry.
- **Headers:**
    - `Idempotency-Key` (String, Optional): A unique key generated by the client to safely retry requests without creating duplicate records.
- **Request Body (JSON):**
  ```json
  {
    "amount": 15000, 
    "category": "Food",
    "description": "Lunch with team",
    "date": "2023-10-25"
  }
  ```
  *(Note: `amount` of 15000 represents ₹150.00 if using integer for paise, or it could just be a decimal `150.00` depending on backend implementation)*
- **Success Response (201 Created):**
  ```json
  {
    "id": "123e4567-e89b-12d3-a456-426614174000",
    "amount": 15000,
    "category": "Food",
    "description": "Lunch with team",
    "date": "2023-10-25",
    "created_at": "2023-10-25T14:30:00Z"
  }
  ```

### 2.2. Get Expenses
- **Endpoint:** `GET /api/expenses`
- **Description:** Retrieves a list of expenses with optional filtering and sorting.
- **Query Parameters:**
    - `category` (String, Optional): Filter expenses by a specific category.
    - `sort` (String, Optional): Sorting criteria. Supports `date_desc` (newest first). Defaults to `date_desc`.
- **Success Response (200 OK):**
  ```json
  [
    {
      "id": "123e4567-e89b-12d3-a456-426614174000",
      "amount": 15000,
      "category": "Food",
      "description": "Lunch with team",
      "date": "2023-10-25",
      "created_at": "2023-10-25T14:30:00Z"
    }
  ]
  ```

## 3. Data Transfer Objects (DTO)

DTOs define the shape of data moving between the client and the server, and within the server layers.

### 3.1. `CreateExpenseDTO` (Request payload)
```typescript
interface CreateExpenseDTO {
  amount: number;       // Must be > 0
  category: string;     // Must not be empty
  description?: string; // Optional
  date: string;         // ISO 8601 Date string (YYYY-MM-DD)
}
```

### 3.2. `ExpenseResponseDTO` (Response payload)
```typescript
interface ExpenseResponseDTO {
  id: string;
  amount: number;
  category: string;
  description: string;
  date: string;
  createdAt: string; // ISO 8601 DateTime string
}
```

### 3.3. `GetExpensesFilterDTO` (Query parameters)
```typescript
interface GetExpensesFilterDTO {
  category?: string;
  sort?: 'date_desc' | 'date_asc'; // Extensible for future sort options
}
```

## 4. Data Access Object (DAO)

The DAO layer abstracts the database interactions, making it easy to swap persistence mechanisms (e.g., from in-memory to SQLite).

### 4.1. `ExpenseDAO` Interface
```typescript
interface ExpenseDAO {
  /**
   * Inserts a new expense into the database.
   * Handles idempotency by checking if the idempotencyKey already exists.
   * If it exists, returns the existing record to prevent duplicates.
   */
  createExpense(expense: ExpenseEntity, idempotencyKey?: string): Promise<ExpenseEntity>;

  /**
   * Retrieves a list of expenses based on provided filters and sorting.
   */
  getExpenses(filters: GetExpensesFilterDTO): Promise<ExpenseEntity[]>;
}
```

### 4.2. `ExpenseEntity` (Internal Database Representation)
```typescript
interface ExpenseEntity {
  id: string;
  amount: number;
  category: string;
  description: string | null;
  date: string;
  idempotencyKey: string | null;
  createdAt: string;
}
```

## Technical Decisions & Trade-offs
- **Money Handling:** Storing amounts as integers (smallest currency unit, e.g., paise/cents) is standard practice to avoid floating-point math errors. We will do this on the backend and format it appropriately on the frontend.
- **Idempotency:** To handle the requirement "Click submit multiple times / Refresh the page after submitting", the frontend will generate a unique identifier (like a UUID) for each form submission and send it as an `Idempotency-Key` header. The backend DAO will ensure that an entry with the same key isn't created twice.
- **Persistence:** For this assignment, we can use an in-memory SQLite database or a simple JSON file for the fastest iteration while maintaining relational/structured querying capabilities. SQLite is highly recommended as it behaves exactly like a real production SQL database.
